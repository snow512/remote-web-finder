# 결정 기록 가이드

아키텍처 결정 기록(ADR)을 효과적으로 작성하기 위한 가이드입니다.

---

## ADR 작성 원칙

1. **결정 시점에 바로 기록** — 나중에 기억에 의존하면 맥락이 소실된다
2. **맥락(Context)을 충분히 기록** — 왜 이 결정이 필요했는지 미래의 독자가 이해할 수 있도록
3. **최소 2개 이상의 선택지를 검토** — 단일 선택지는 결정이 아니라 통보
4. **장단점을 균형 있게 작성** — 선택한 안의 단점도, 포기한 안의 장점도 기록
5. **수락된 결정은 수정하지 않는다** — 결론을 바꾸려면 새 ADR로 대체(Supersede)

## 결정이 필요한 상황

- 기술 스택 선택 (언어, 프레임워크, 데이터베이스 등)
- 아키텍처 패턴 변경 (모놀리식 → 마이크로서비스 등)
- 외부 서비스/라이브러리 도입 또는 교체
- 데이터 모델 설계 방향
- 배포/인프라 전략 변경
- 성능 vs 유지보수성 등 트레이드오프가 있는 결정

## 좋은 ADR 작성 요령

### 맥락 섹션
- 현재 상황과 문제점을 구체적으로 기술
- 수치나 데이터가 있으면 포함 (응답 시간, 에러율 등)

### 선택지 섹션
- 각 선택지의 장점과 단점을 구체적으로 나열
- "좋다/나쁘다"가 아닌 객관적 기준으로 비교
- PoC(Proof of Concept) 결과가 있으면 포함

### 결정 섹션
- 선택한 안과 그 이유를 명확히 기술
- 포기한 안을 선택하지 않은 이유도 포함

### 결과 섹션
- 이 결정으로 인해 변경되는 것을 구체적으로 나열
- 추가로 필요한 작업이 있으면 피쳐/타스크와 연결

## 상태 관리

- **Proposed**: 제안 단계 — 팀 리뷰 대기
- **Accepted**: 승인되어 적용 중
- **Deprecated**: 더 이상 유효하지 않지만 대체 결정 없음
- **Superseded**: 새로운 결정으로 대체됨 — `superseded-by` 필드에 새 ADR 기록
