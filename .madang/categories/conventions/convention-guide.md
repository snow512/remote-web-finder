# 코드 컨벤션 가이드

프로젝트 전체에서 일관된 코드를 유지하기 위한 가이드입니다.

---

## 컨벤션 작성 원칙

1. **좋은 예와 나쁜 예를 반드시 포함** — 규칙만 나열하면 해석이 달라질 수 있다
2. **하나의 문서 = 하나의 주제** — 명명 규칙과 파일 구조를 하나에 섞지 않는다
3. **강제 규칙과 권장 규칙을 구분** — 반드시 지켜야 할 것과 권장 사항을 명확히 표시
4. **예외를 명시** — 규칙을 따르지 않아도 되는 상황을 문서화
5. **린터/포매터 설정과 연계** — 자동화 가능한 규칙은 도구로 강제

## 필수 컨벤션 목록

프로젝트 시작 시 다음 컨벤션을 우선 정의하세요:

### 1. 코딩 스타일 (`conv-coding-style.md`)
- 들여쓰기: 탭 vs 스페이스, 크기
- 따옴표: 작은따옴표 vs 큰따옴표
- 세미콜론 사용 여부
- 최대 줄 길이
- 후행 쉼표(trailing comma) 규칙
- 중괄호 스타일 (K&R vs Allman)

### 2. 명명 규칙 (`conv-naming.md`)
- **변수/함수**: camelCase
- **클래스/컴포넌트**: PascalCase
- **상수**: UPPER_SNAKE_CASE
- **파일명**: kebab-case (또는 프레임워크 규칙)
- **데이터베이스**: snake_case
- **Boolean 변수**: `is`, `has`, `can`, `should` 접두사
- **이벤트 핸들러**: `handle` 접두사 (`handleClick`, `handleSubmit`)

### 3. 파일/폴더 구조 (`conv-file-structure.md`)
- 기능 기반 vs 레이어 기반 디렉토리 구조
- 인덱스 파일(barrel export) 사용 규칙
- 테스트 파일 위치 (co-located vs 별도 폴더)
- 공유 모듈 구성 방식

### 4. Git 규칙 (`conv-git.md`)
- **커밋 메시지**: Conventional Commits 형식 (`feat:`, `fix:`, `refactor:` 등)
- **브랜치 명명**: `feature/`, `fix/`, `hotfix/` 접두사
- **PR 규칙**: 제목 형식, 리뷰어 지정, 체크리스트
- **머지 전략**: squash, rebase, merge commit 중 선택

### 5. 에러 처리 (`conv-error-handling.md`)
- 예외 처리 패턴 (try-catch 범위, 에러 전파)
- 에러 로깅 규칙 (레벨, 포맷)
- API 에러 응답 형식 (에러 코드, 메시지 구조)
- 사용자 대면 에러 메시지 규칙

## scope 필드 활용

| scope | 적용 범위 |
|-------|-----------|
| `project` | 프로젝트 전체에 적용 |
| `frontend` | 프론트엔드 코드에만 적용 |
| `backend` | 백엔드 코드에만 적용 |
| `shared` | 공유 코드/라이브러리에 적용 |

## 컨벤션 도입 절차

1. 컨벤션 문서를 Draft로 작성
2. 팀원 리뷰 및 합의
3. 린터/포매터 설정 업데이트 (자동화 가능한 경우)
4. 기존 코드 점진적 적용 (일괄 변환 주의)

## 컨벤션 변경

- 컨벤션은 합의에 의해서만 변경
- 변경 시 `last-updated` 필드 업데이트
- 대폭 변경 시 결정 기록(ADR)으로 근거 문서화 권장
- 폐기된 컨벤션은 `.deprecated/`로 이동
