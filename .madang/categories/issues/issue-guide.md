# 이슈 관리 가이드

프로젝트의 버그와 장애를 체계적으로 추적하고 해결하기 위한 가이드입니다.

---

## 이슈 작성 원칙

1. **재현 가능하게 작성** — 증상만 기록하지 말고 재현 절차를 포함한다
2. **하나의 이슈 = 하나의 문제** — 여러 버그를 하나의 이슈에 묶지 않는다
3. **증상과 원인을 분리** — 증상 섹션에 추측을 섞지 않는다
4. **스크린샷/로그를 첨부** — 가능하면 에러 메시지, 스택 트레이스를 포함

## 심각도 기준

| 심각도 | 기준 | 대응 시간 |
|--------|------|-----------|
| Critical | 서비스 중단, 데이터 손실 | 즉시 대응 |
| High | 핵심 기능 장애, 워크어라운드 없음 | 당일 내 |
| Medium | 기능 장애, 워크어라운드 존재 | 1주 이내 |
| Low | 사소한 불편, 외관 문제 | 다음 릴리즈 |

## 해결 프로세스

1. **이슈 등록** → status: Open
2. **원인 분석 시작** → status: Investigating
3. **수정 완료 및 검증** → status: Resolved, `.resolved/`로 이동
4. **해결 방법 섹션을 반드시 채운다** — 같은 문제 재발 시 참조할 수 있도록

## 연관 관계

- 이슈 해결을 위해 타스크가 필요하면 `related-task` 필드에 연결
- 이슈에서 발견한 근본 원인이 설계 문제라면 결정 기록(ADR)으로 연결 검토
