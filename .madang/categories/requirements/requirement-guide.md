# 요구사항 작성 가이드

요구사항을 명확하고 검증 가능하게 작성하기 위한 가이드입니다.

---

## 요구사항 작성 원칙

1. **검증 가능하게 작성** — "빨라야 한다" (X) → "페이지 로딩 시간 2초 이내" (O)
2. **하나의 요구사항 = 하나의 조건** — 복합 조건은 분리한다
3. **구현 방법이 아닌 "무엇"을 기술** — "Redis를 사용한다" (X) → "세션을 서버 재시작 후에도 유지한다" (O)
4. **인수 조건을 반드시 포함** — 요구사항 충족 여부를 판단할 수 있는 체크리스트

## 카테고리 구분

| 카테고리 | 설명 | 예시 |
|----------|------|------|
| Functional | 시스템이 수행해야 할 기능 | "사용자는 비밀번호를 변경할 수 있다" |
| Non-Functional | 품질 속성 (성능, 보안 등) | "동시 접속 1000명 지원" |
| Constraint | 기술/비즈니스 제약 | "PostgreSQL 사용 필수" |

## 우선순위 판단 기준

- **1-High**: 없으면 시스템이 목적을 달성할 수 없는 핵심 요구사항
- **2-Medium**: 있으면 사용성이 크게 개선되는 중요 요구사항
- **3-Low**: 있으면 좋지만 없어도 시스템 운영에 지장 없는 요구사항

## 상태 관리

- **Draft**: 초안 — 아직 이해관계자 확인 전
- **Confirmed**: 이해관계자가 확인하고 승인한 요구사항
- **Changed**: 요구사항 내용이 변경됨 — 변경 이력 테이블에 기록 필수
- **Archived**: 더 이상 유효하지 않은 요구사항

## 피쳐와의 관계

- 요구사항은 "무엇"을 정의하고, 피쳐는 "어떻게 구현할지"를 정의
- 하나의 요구사항이 여러 피쳐로 분해될 수 있음
- 요구사항 파일에서 관련 피쳐를 링크하여 추적성 유지
