# 스펙 작성 가이드

기술 참조 문서를 일관되고 유용하게 유지하기 위한 가이드입니다.

---

## 스펙 작성 원칙

1. **하나의 스펙 = 하나의 주제** — DB 스키마, API 설계, 아키텍처를 각각 별도 파일로
2. **코드가 아닌 "왜"를 설명** — 코드를 복붙하지 말고 설계 의도와 제약 사항을 기록
3. **살아있는 문서로 유지** — 코드가 변경되면 스펙도 함께 업데이트
4. **변경 이력을 기록** — 언제 무엇이 바뀌었는지 추적 가능하게

## 스펙 유형별 작성 요령

### 데이터베이스 스키마
- 테이블/컬렉션 구조를 표로 정리
- 인덱스, 관계, 제약 조건을 명시
- 마이그레이션 전략을 포함

### API 설계
- 엔드포인트, 메서드, 요청/응답 형식을 표로 정리
- 인증/인가 요구사항을 명시
- 에러 응답 형식과 코드를 정의

### 아키텍처
- 컴포넌트 간 관계를 다이어그램(ASCII)으로 표현
- 데이터 흐름을 설명
- 외부 의존성과 연동 방식을 명시

## 명명 규칙

- 파일명은 주제를 나타내는 간결한 영문: `database-schema.md`, `api-design.md`
- 날짜 접두사 불필요 — 스펙은 참조 문서이며 시계열 문서가 아님
