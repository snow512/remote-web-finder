# 티켓 관리 가이드

프로젝트의 피쳐와 타스크를 체계적으로 관리하기 위한 가이드입니다.

---

## 피쳐 작성 원칙

1. **하나의 피쳐 = 하나의 사용자 가치** — 여러 가치를 묶지 말고 분리한다
2. **피쳐 제목은 동사로 시작** — "~을 추가한다", "~을 개선한다" 형태로 명확히 작성
3. **인수 조건을 반드시 포함** — 피쳐가 "완료"되었는지 판단할 수 있는 객관적 기준
4. **단계(Phase)로 분할** — 피쳐가 3개 이상의 타스크를 포함하면 단계별로 나눈다
5. **우선순위는 비즈니스 가치 기준** — 기술적 난이도가 아닌 사용자/비즈니스 관점에서 판단

## 타스크 작성 원칙

1. **하나의 타스크 = 하루 이내 완료 가능한 작업** — 더 크면 분할한다
2. **체크리스트는 2~5개 항목** — 너무 많으면 여러 타스크로 나눈다
3. **타스크 제목은 구체적으로** — "리팩토링" (X) → "UserService의 인증 로직을 미들웨어로 분리" (O)
4. **독립 타스크도 허용** — 모든 타스크가 반드시 피쳐에 속할 필요 없음

## 칸반 보드 운영

1. **Doing은 동시에 3개 이하** — WIP(Work In Progress) 제한으로 집중도 유지
2. **Plan → ToDo 이동은 스펙이 충분할 때** — 불명확한 피쳐를 ToDo에 넣지 않는다
3. **Done 이동은 사용자 확인 후에만** — 자의적으로 완료 처리하지 않는다
4. **미소속 피쳐는 정기적으로 정리** — 그룹에 배정하거나 아카이브 처리

## 계획모드(Plan Mode) 워크플로우

계획모드에서 작업 계획을 수립한 후에는 반드시 피쳐와 타스크 문서를 먼저 생성한 뒤 구현 작업을 수행한다.

1. 계획모드에서 작업 범위와 단계를 정리한다
2. 계획 결과를 기반으로 피쳐 파일(`docs/features/`)을 생성한다 — 피쳐 규칙에 따라 작성
3. 피쳐의 하위 타스크 파일(`docs/tasks/`)을 생성한다 — 타스크 규칙에 따라 작성
4. 피쳐를 적절한 그룹(기본: `group-plan.md`)에 등록한다
5. 문서 생성이 완료되면 타스크 순서대로 구현 작업을 수행한다

## 타스크 진행 추적

개발 작업을 수행할 때 관련 타스크와 피쳐의 상태를 자동으로 추적한다.

### 상태 업데이트 시점
1. **작업 시작**: 관련 타스크의 frontmatter `status`를 `In Progress`로 변경
2. **작업 완료**: 타스크의 `status`를 `Done`으로 변경, 체크리스트 `- [ ]`를 `- [x]`로 체크
3. **커밋 시**: 커밋에 포함된 변경 내용과 관련된 타스크를 찾아 상태를 갱신

### 피쳐 상태 연동
- 하위 타스크 중 하나라도 `In Progress`면 → 피쳐도 `In Progress`
- 모든 하위 타스크가 `Done`이면 → 피쳐도 `Done`
- 피쳐 파일의 하위 타스크 테이블에서 해당 타스크 행의 상태 컬럼도 함께 업데이트

### 관련 타스크 매칭 방법
- 현재 작업 내용(수정 파일, 구현 주제)과 `docs/tasks/`의 타스크 제목/체크리스트를 비교
- 매칭되는 타스크가 없으면 강제로 생성하지 않음 — 추적 없이 진행

## 명명 규칙

- 피쳐 파일: `feature-{YYYY-MM-DD}-{영문-slug}.md`
- 타스크 파일: `task-{YYYY-MM-DD}-{영문-slug}.md`
- slug는 소문자 영문, 하이픈 구분, 5단어 이내로 간결하게
